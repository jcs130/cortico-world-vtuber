# 连续语音与音色排查

## 思考、执行与播放的重叠

`vtuber_act` 受理后立即返回，合成和播放由演出引擎继续；受理不等于播放完成。语音积压、重复台词或同轮次数拒收只影响该条语音，不再通过 `endsTurn` 结束宿主的整轮决策。主体可以继续核验现场、思考或提交独立游戏任务；不要在没有新内容或队列变化时反复重投同一台词。

`speechPlanningLeadSec` 默认 12 秒，0 关闭。引擎已确认正在播放语音、剩余在播与排队时长进入该窗口时，每个已受理队列版本只投递一次 `vtuber.speech.window`。主决策正在运行时读数仅 piggyback；主线程空闲时 flush 交给宿主唤醒，仍由宿主管理单一决策生命周期与暂停。事件不另开模型、不接管身体、不要求发言。歌曲、没有播放时钟、过期心跳和停机状态不触发。未合成部分的剩余时长仍是估计。

通知按宿主的延迟渲染契约投递：真正投递时重新核对队列版本、在播状态和心跳；已经播完、换队列或过期的通知丢弃。后续请求使用最新演出读数替换旧窗口。宿主准备下一步时必须读取最新现场和任务终态；语音还在说什么不能作为游戏动作已生效的证据。现有整句收齐播放、音色、取消与队列顺序不变。提前通知只减少可避免的唤醒空档，不能加快慢模型或慢 TTS，也不承诺每段语音无缝衔接。

同一条自然语句里的 `<动作>` 使用一次流式合成。动作按播放时间轴执行：开启逐字对齐时使用对齐结果；关闭时使用已有语速估计，收流后用真实总时长修正。估计不等于逐字精确对齐，也不启动额外模型调用。`【动作】` 的阻断语义保留。

这减少了内联表演导致的独立合成次数，并保留句内韵律连续性。固定参考音频、种子和模式仍不能保证不同文本有相同的音高、情绪或听感。不能把音色设置相同当作主观质量已通过。

排查时对齐：说话轮次与原文 → 分段请求 → 参考音频哈希、模式和种子 → 原始 PCM 哈希与采样率 → 声卡实际播放采样率。声音只做本地短窗采样；不要把音频写进 Agent 记忆或默认永久保存。

2026-10-14 的 N1 样本中，54 次请求使用同一参考、种子 42 和 ref_continuation；7 段现役 PCM 与后端哈希一致。存在内联动作将一句话切成两个独立请求的情况。连续合成的短窗对照只支持减少此类重新起声，不能证明全部句间差异已经解决。
